# DMA Connect

Expo SDK 57 / React Native app for Dr. Mangesh Amale Foundation. The original foundation logo, white surfaces and purple accents are used throughout. Expo Router routes live in `src/app/`.

## Run

The new backend email signup/login flow is configured with `EXPO_PUBLIC_BACKEND_API_URL` in `.env.development`. Start it with `npm start` or `npm run web`; it uses the supplied REST API and does not require Firebase emulators. See [REST authentication](docs/REST-AUTH.md) for endpoint contracts, the signup area dropdown and backend requirements. The Firebase workflow below is still available through `npm run start:demo`.

Use Node.js **24.12 or later**. Install both app and backend dependencies:

```sh
npm ci
npm ci --prefix functions
# Expo Go with the configured REST API
npm start
```

Live SMS OTP is deferred and will use **Twilio Verify** later. The separate Firebase demo uses Auth emulators for simulated codes. Live Firebase SMS calls are disabled on both web and native clients. See [OTP integration plan](docs/OTP-INTEGRATION.md).

**Test OTP works in Expo Go, development builds and web when the local demo is running.** Expo Go uses the Auth emulator's REST interface and the Firebase JS SDK; development builds containing React Native Firebase use the native verification flow. The emulator generates a fresh six-digit code and the app displays it on the next screen. There is no fixed OTP and no SMS is sent. Expo generates `ios/` and `android/` from `app.json` and config plugins. Do not edit generated native projects.

```sh
npm run ios
npm run android
npx eas-cli@latest build --platform android --profile development
npx eas-cli@latest build --platform ios --profile development-simulator
```

On Windows, use the Android EAS command above to build in the cloud without a local Android SDK. Install the resulting development APK on your phone, then run `npx expo start --dev-client` and open **DMA Connect** on the phone. `npm start` uses Expo Go by default. Local `npm run android` requires Java and the Android SDK; local iOS builds require macOS.

If you see `Native module NativeRNFBTurboApp is not registered`, update to the guarded phone-auth implementation in this checkout. Test OTP now falls back to the local emulator in Expo Go. Native Firebase itself still requires an installed development build; npm installation or a Metro cache reset cannot add native modules to an app binary.

The install/prebuild hooks apply narrow path-quoting fixes to Expo Constants 57 and the generated React Native bundle phase so local iOS builds support workspace folders containing spaces. Generated native files are regenerated by Expo/CocoaPods.

For signed device builds use the `development`, `preview` or `production` EAS profiles. Set `EXPO_PUBLIC_BACKEND_API_URL` in the build environment to use REST authentication. Without that variable, the app uses the original Firebase workflow. Production exports always ignore the Firebase emulator flag.

## Implemented flow

- REST email signup/login with persistent sessions and a committee directory. Signup lists only active `area` committees, submits their numeric `committeeId` as `areaId`, and currently allows no photograph (`photoPaths: []`). See [REST authentication](docs/REST-AUTH.md). The remaining items below describe the separate Firebase workflow.
- Own-phone OTP sign-in and signup in emulator mode; manual code entry, resend cooldown, iOS SMS autofill and native verification handling. Existing email/password users can sign in and verify/link their own phone in the emulator while preserving their UID. Live OTP awaits the later Twilio integration.
- Central **Super Admin** configures the organisation. Presidents follow State → District → Taluka → ward → village/local. Cells report through District. Only State, District and Taluka have one maker and one separate checker each.
- Super Admin creates committee units and configures operational seats. Makers submit president/member invitations and account changes; the same team’s checker must approve. Presidents can view the work. Approved invitations expire after 14 days and activate after the recipient verifies their invited phone and completes their profile.
- Member signup collects name, email, verified mobile, residence, DOB, home area, one required photograph and up to two additional photographs. Facebook, LinkedIn and Instagram fields are included and optional. Birthday email preference is editable.
- Members request geographic and cell affiliations independently. Taluka checkers handle area/ward/local requests; District checkers handle cell requests. A checker cannot approve their own request. Requesting membership does not grant an operational role.
- Makers submit full member profiles with photographs for checker approval. Pending records remain outside member counts. Later signup with the same verified mobile claims the approved existing record. A canonical identity is counted once across affiliations.
- Staff tabs: **Add member**, **Statistics**, **Members**. Member tabs: **My profile**, **Committees**, **Account**. iOS uses native tabs with Liquid Glass on supported iOS versions; Android and web use the white/purple tab bar.
- Members directory uses server pagination (50 rows), full-scope name/mobile prefix search, committee filtering and private profile/photo details. Statistics use server aggregates, India date boundaries and unique-person totals.
- Assigned checkers suspend/restore affiliations handled by their team. Presidents can view these links. Suspension preserves independent affiliations and cannot be bypassed by reapplying.
- Real-time owner snapshots and private workspace invalidation refresh approvals, profiles, counts and directories.

Initial catalogue: **Belapur, Nerul, Vashi, Turbhe, Kopar Khairane, Ghansoli, Airoli, Digha**, plus **OBC Cell, Maratha Cell, Muslim Cell**. Existing NMMC area labels remain stable; the organisational Taluka level is not an official list of revenue talukas. Super Admin configures ward/local names. Each committee has one president; only State, District and Taluka have maker/checker seats.

## Backend

Project **`dma-connect-foundation`** (number `536704319606`). Named **Enterprise Native Firestore database `dma-connect`**, Mumbai **`asia-south1`**. Public client configuration is in `src/services/firebase-config.ts`; iOS and Android service files contain public app configuration, not administrator credentials. Native bundle/package: **`org.dmafoundation.connect`**.

The backend is **Cloud Functions for Firebase v2, Node.js 24**, in Mumbai. `dmaApi` validates and executes trusted mutations and scope-checked reads. Firestore and Storage clients cannot write membership data or fetch private photographs directly. Photo uploads are resized to JPEG, stored privately, and delivered through a checked callable endpoint; public download tokens are not generated.

```text
accounts/{authUid}                 trusted account role and appointment
people/{personId}                  canonical private profile and membership scopes
committees/{committeeId}           state / district / taluka / ward / local / cell hierarchy and team seats
requests/{personId__committeeId}   independent approval decisions
affiliations/{personId__committeeId}
phoneIndex/{sha256Phone}           private identity deduplication
invitations/{sha256Phone}          private, expiring appointments
workspaceEvents/{authUid}          private real-time invalidation
workItems/{id}                    immutable maker submission and checker decision
activity/{id}                     administrative audit records
birthdayDeliveries/{person_year}  annual send ledger and retry state
system/birthday-service           job status for Super Admin
```

Classic indexed Firestore queries are deliberate here: the app requires real-time snapshots and transactional scope/access maintenance, also exercised in the emulator. Enterprise sparse indexes are declared in `firestore.indexes.json`. The emulator does not enforce compound indexes, so deployment and READY status must be verified separately.

## Birthday emails

A scheduled function checks every 30 minutes from **9:00 AM India time**. An opted-in, active member with a claimed active account, matching Firebase-verified email and primary photograph receives a foundation-branded birthday greeting with their photograph embedded as an attachment. February 29 birthdays use February 28 in non-leap years.

Resend is the email provider. No key ships to the app. `RESEND_API_KEY` is a server Secret Manager secret; `BIRTHDAY_FROM_EMAIL` must use a verified sender domain. Known send failures retry for seven days, up to 80 queued records per run. Each person has one annual delivery record across committees. Resend idempotency keys protect retry requests for 24 hours; ambiguous results after 23 hours are flagged for operator review instead of risking a duplicate. Provider acceptance is recorded as `sent`; it is not a guarantee of inbox delivery. History shows failures and review states.

Firebase/React Native Firebase and Resend SDKs are free libraries. App development continues without enabling Firebase billing or activating live SMS. Twilio Verify is the selected future SMS provider; its server credentials must never be shipped in the app. The current Cloud Functions, Storage and Scheduler production deployment separately requires a billing-enabled Firebase project, so changing the SMS provider alone does not deploy that backend. Resend's free email allowance has a daily/monthly cap. See [Firebase pricing](https://firebase.google.com/pricing) and [Resend pricing](https://resend.com/pricing).

## Local testing

Requires **Java 21+**, Node 24 and dependencies above. These commands use a separate `demo-dma-connect` project and the named `dma-connect` database. Run them in two terminals (PowerShell works):

```sh
# Terminal 1: wait for all emulators to be ready
npm run emulators

# Terminal 2: prepare the demo catalogue and start Expo Go
npm run start:demo

# Or preview in the browser / an installed development build
npm run start:demo -- --web
npm run start:demo -- --dev-client
```

`start:demo` selects the Firebase workflow, checks the four local services, enables test mode, chooses the computer's LAN IPv4 address and seeds/reuses only the demo Super Admin and committee catalogue. Scan the current QR code in Expo Go on a phone connected to the same network. The emulators listen on the LAN in this demo configuration. If your computer has multiple network adapters, set `$env:EXPO_PUBLIC_FIREBASE_EMULATOR_HOST = 'YOUR_COMPUTER_LAN_IP'` in PowerShell before starting. Allow the emulator ports through your local firewall if needed. Metro uses port 8081 by default.

The checked-in `.env.development` selects REST authentication. Its Firebase emulator flag applies only when the REST API URL is cleared, as `start:demo` does automatically. On native devices in that demo, the emulator host defaults to the computer address in Expo's Metro manifest; `localhost` on a phone would point at the phone itself. Fully reload Expo Go after switching servers or environment settings. `npm run start:live` selects the separate live Firebase email flow; live SMS remains unavailable.

To log in locally, enter a 10-digit Indian mobile and tap **Send verification code**. The next screen shows **Test OTP**: enter that six-digit code and tap **Verify and continue**. Use `9000000001` for the seeded demo Super Admin, or a different test number to create a member account. Complete the profile on first signup.

Super Admin: `9000000001`. A fresh demo has the committee catalogue and this central appointment; sign in, complete the profile, then configure maker/checker seats and invitations from that account. Other mobile numbers start as members unless a matching appointment has been configured.

The Auth emulator generates a new code for each request; it does not deliver SMS. The app displays only the code matching the requested phone and verification session, in development emulator mode. Codes are also printed in the emulator log. Set `EXPO_PUBLIC_FIREBASE_EMULATOR_HOST` to `10.0.2.2` for the standard Android emulator if required. Release bundles ignore emulator settings; select the local Firebase demo explicitly with `start:demo`.

```sh
npm run lint
npm run typecheck
npm test
npm run test:otp  # requires npm run emulators to be running
npm test --prefix functions
npm run test:rules
npm run test:integration
npx expo-doctor
npx expo export --platform all
```

`test:integration` starts all four emulators and clears only their **demo** test data. It covers OTP verification, forged roles, scoped invitations, separate approvals, private photos, suspension, deduplication, directory pagination, named-database rules, birthday attachments, retries and opt-out. Scheduled jobs are called directly with a captured test mailer; no real email is sent. Run emulator-starting scripts with existing emulators stopped. The standalone rules suite tests the same rules in the default test database, and integration tests validate the named database used by the app.

## Live activation and migration

Follow [Deployment](docs/DEPLOYMENT.md). Development runs against emulators without waiting for billing. Live backend activation is a later step, and live OTP integration is explicitly deferred to Twilio. Do not publish the client pointing to production until deployment and the required real OTP/email smoke tests pass.

The previous `presidents/{uid}/members/{mobile}` records remain intact. Migration is explicit, uses a confirmed destination committee, reports duplicate identities, preserves original sources/timestamps and never automatically turns a legacy descriptive role into administrator access. Setup and migration scripts are dry runs unless `--apply` is passed.
